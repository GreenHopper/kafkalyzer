# Design

## Context

See `proposal.md` for motivation; `specs/desktop-bridge-build/spec.md` for the behaviour being introduced. Observed state:

- The bridge crate `rust_lib_kafkalyzer` (workspace root `rust/`, `[lib] crate-type = ["cdylib","staticlib"]`) is built
  by the vendored Cargokit scaffold in `rust_builder/`: a macOS podspec, a Windows `CMakeLists.txt`, a Linux CMake
  include, and a Dart `build_tool`. `pubspec.yaml` depends on it as `rust_lib_kafkalyzer: { path: rust_builder }`,
  and `linux/flutter/generated_plugins.cmake` plus `windows/flutter/generated_plugins.cmake` list the plugin.
- `flutter_rust_bridge` is pinned to `2.11.1` in `pubspec.yaml`, `rust/Cargo.toml` (`=2.11.1`) and
  `rust/kafkalyzer-mcp/Cargo.toml`. `scripts/quality_gates.sh` refuses to regenerate bindings unless the pubspec pin,
  the Cargo pin and the installed `flutter_rust_bridge_codegen` version are all identical.
- `packages/velopack_flutter` is vendored, uses Native Assets already (`hook/build.dart` with
  `RustBuilder(cratePath: 'rust', assetName: 'src/lib.rs')`), pins `flutter_rust_bridge: 2.11.1`, and carries
  `rust/rust-toolchain.toml`. It builds in the Linux, macOS and Windows CI jobs today.
- `native_toolchain_rust` 1.0.4 (the version resolved for velopack today) runs
  `rustup run <channel> cargo build [--release] --manifest-path <crate>/Cargo.toml --package <crate>
  --target <triple> --target-dir <hook output>/target`. It **requires** `<cratePath>/rust-toolchain.toml` with an
  exact channel and a `targets` list containing the requested triple, and it requires `crate-type` to contain both
  `staticlib` and `cdylib`. It calls `Process.run` with an extra environment map but with the default
  `includeParentEnvironment: true`, so the CI shell's `OPENSSL_DIR`, `PKG_CONFIG_PATH` and vcpkg variables reach
  cargo; `extraCargoEnvironmentVariables` exists as the explicit escape hatch. On macOS it strips Xcode
  `Contents/Developer/` entries from `PATH` before invoking cargo.
- The macOS job currently forces `flutter config --no-enable-swift-package-manager`, and the last CI failure named
  exactly two SPM-incompatible plugins: `flutter_secure_storage_macos` (fixed by the 10.3.4 upgrade) and
  `rust_lib_kafkalyzer`. The macOS build also compiles an x86_64 leg, which pulls `krb5-src`/OpenSSL vendored builds
  into a cross-compile that autoconf refuses.

## Goals / Non-Goals

**Goals:**
- One build path for the bridge library across `flutter run`, `flutter test` and `flutter build`, on three OSes.
- A native build failure that prints the cargo/cc error, not a wrapper exit code.
- macOS artifacts for arm64 only, with Swift Package Manager enabled and no SPM warning.
- Cache keys and paths that match where the new build actually puts its objects.

**Non-Goals:**
- No change to bridge function signatures, DTOs, stored profile/search/script data, or any Dart UI code —
  the migration is build wiring only, so the backwards-compatibility rules of the project config stay untouched.
- No new logic to place in a layer: nothing moves into `kafkalyzer-core` or `kafkalyzer-kafka`, and no Dart
  module boundary changes. Crate names and locations stay as they are (roadmap decision E2).
- No Intel macOS artifacts, no universal binaries, no iOS/Android targets.

## Decisions

**D1 — Use the FRB Native Assets backend, generated by the codegen tool.**
`flutter_rust_bridge_codegen integrate --integration-backend native-assets` writes `hook/build.dart` and rewrites the
pubspec wiring. Alternative considered: keep Cargokit and leave SPM disabled — it keeps the last non-SPM plugin, keeps
the Xcode/CMake shim, and keeps the opaque `MSB8066 … exit code -1` failure mode that cost a full CI round trip on
Windows. Alternative: hand-write the hook — the generator's output is the documented shape and is what velopack has.

**D2 — Copy the velopack_flutter pattern rather than inventing one.**
Same `code_assets ^1.0.0`, `hooks ^1.0.3`, `native_toolchain_rust ^1.0.3` dependency set and the same
`RustBuilder(cratePath: 'rust', assetName: 'src/lib.rs')` call. It is the house implementation of this exact problem
and is already green on all three CI jobs. Two native-assets packages in one app (velopack + kafkalyzer) is what
velopack's own example apps do.

**D3 — Pin `rust/rust-toolchain.toml`, not a root-level one.**
The builder looks for the file inside the crate directory and refuses a bare `stable`/`beta`/`nightly` channel and any
target triple missing from `targets`. Content: exact channel equal to the Rust version the CI jobs install today, and
`targets` limited to `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`,
`x86_64-pc-windows-msvc`. Alternative considered: rely on the machine default toolchain — impossible, the builder
errors out; alternative: pin at repo root — not read by the builder. Consequence to keep: `cargo test`, `clippy` and
`kafkalyzer-mcp` now also resolve to that pinned channel, so the CI Rust setup and the pin MUST stay equal or every
job downloads a second toolchain.

**D4 — Keep the existing crate and feature wiring, change only who invokes cargo.**
`crate-type` already satisfies the validator; the platform-specific rdkafka feature sets in
`rust/kafkalyzer-kafka/Cargo.toml` (vcpkg on Windows, system SASL on Linux, vendored SSL/GSSAPI on macOS) stay. The
hook does not pass `features`, so the crate's own dependency table keeps deciding them. Alternative considered: move
feature selection into the hook — two places deciding one thing, and `cargo test` would drift from the app build.

**D5 — Re-derive the CI caches from the actual output directory.**
The builder uses `--target-dir <hook output>/target`, i.e. not `rust/target`, so today's cache paths
(`build/windows/x64/plugins/rust_lib_kafkalyzer/cargokit_build`,
`build/macos/Build/Intermediates.noindex/Pods.build/Release/rust_lib_kafkalyzer.build`) cache a directory that stops
existing. A discovery step records the real path locally and in CI, and the cache key becomes
`os + flutter version + toolchain channel + rust/Cargo.lock hash`. The temporary Windows pre-build step
(`cargo build --release -p rust_lib_kafkalyzer` before `flutter build windows`) is removed again — its only purpose was
to surface cargo output that Cargokit swallowed, and the new build path prints it by itself.

**D6 — macOS arm64 by Xcode build setting plus a CI assertion, not by build flags.**
`EXCLUDED_ARCHS = x86_64` in the project-level Release configuration (already on `spike/keyring-ci`), because Flutter
drives the Release build with `-destination generic/platform=macOS`, which overrides `ONLY_ACTIVE_ARCH` (attempt 1,
commit `c87a29a`, did nothing) and makes the project setting the only lever Flutter honours. A CI step then reads the
resolved `ARCHS` and fails the job if it is not `arm64`, so a Flutter or Xcode update that drops the setting shows up as
a red job instead of a silent 2x build. Alternative: pass `-arch arm64` — Flutter does not forward it; alternative:
build universal — costs a cross-compiled vendored Kerberos/OpenSSL that GitHub's arm64-only runners cannot do.

**D7 — Turn SPM on in the macOS job once the plugin is gone.**
Replace `flutter config --no-enable-swift-package-manager` with the enabling flag. The last CI log named only
`flutter_secure_storage_macos` and `rust_lib_kafkalyzer` as unsupported; both are then fixed, and the remaining
CocoaPods plugins stay in Flutter's hybrid mode. If a warning for a third plugin appears, it is reported in the job log
and the release artifact is treated as affected (spec scenario), not silently accepted.

**D8 — Bump all FRB pins together and re-apply the velopack patches.**
`pubspec.yaml`, `rust/Cargo.toml`, `rust/kafkalyzer-mcp/Cargo.toml` and `packages/velopack_flutter/pubspec.yaml` all go
to `2.13.0`, and the local codegen gets installed at exactly that version before regeneration, because
`scripts/quality_gates.sh` compares all three. Alternative considered: bump only the app pins and leave velopack at
2.11.1 — pub would reject two versions of `flutter_rust_bridge` in one resolution.

## Risks / Trade-offs

- **`krb5-src` under an explicit `--target` triple** — the builder always passes `--target aarch64-apple-darwin`, and
  autoconf can treat an explicit target as cross-compiling, which is the error class that killed the x86_64 leg.
  → Mitigation: the first spike builds only the macOS hook and reports the outcome before any other wiring is
  committed; ordered fallbacks are (a) pre-seed the krb5 configure cache variables the vendored build probes,
  (b) switch macOS to the system GSSAPI instead of `gssapi-vendored`, (c) ask for a product decision on dropping
  Kerberos SASL on macOS. Option (c) changes features and is not taken silently.
- **Cache poisoning** — a wrong cache path plus `restore-keys` can restore a half-populated target directory, which is
  a candidate explanation for the original Windows `MSB8066` failure. → Mitigation: first migration run has caching
  disabled, the path is proven from a real run, then caching is re-enabled with a lockfile+toolchain cache key.
- **Regenerated bindings differ beyond the loader** — 2.13 regenerates `frb_generated.dart`/`frb_generated.rs`.
  → Mitigation: regeneration in one commit, guarded by the bindings drift check, then `cargo test`, `flutter analyze`
  and the existing Dart tests; no bridge signature changes are part of this change.
- **`flutter test` now triggers the build hook** — if the test runner builds code assets, the test job needs the native
  prerequisites. → Mitigation: verify in the Linux test job; they are already installed there for `cargo test` per the
  `static-analysis-gates` native-prerequisites requirement, so this is expected to be a no-op.
- **Toolchain pin versus CI Rust setup** — a pinned channel that differs from the CI-installed Rust makes every job
  download a second toolchain and slows all builds. → Mitigation: one commit sets the pin and the CI Rust version to
  the same number, and the CI log line `rustup show active-toolchain` is checked once.
- **Two packages pinning native assets** — velopack and the app must resolve to one version set. → Mitigation: same
  version constraints as velopack's pubspec, verified by `flutter pub get` in the first spike task.
- **Rollback** → the migration is one revertible commit chain: restore `rust_builder/`, the pubspec path dependency,
  the FRB 2.11.1 pins and the CMake/plugin-registrant files; the generated 2.13 bindings revert with them. Keep the
  arm64 `EXCLUDED_ARCHS` setting on rollback — it is independent of the build backend.

## Migration Plan

1. Spike the build hook on Linux (cheapest, no vendored Kerberos) and macOS (the risky one) before touching pins.
2. Bump the four FRB pins, install the matching codegen, run `integrate`, regenerate bindings, delete `rust_builder/`.
3. Update CI: remove Cargokit caches, add the discovered cache path, flip the SPM flag, drop the Windows pre-build step.
4. Prove all three release jobs plus the test job on this branch, then merge.

Rollback: revert the branch commits in reverse order; the `EXCLUDED_ARCHS` and SPM-flag decisions are kept because they
do not depend on the build backend.

## Findings From The Spike

Measured on Linux with `rust/rust-toolchain.toml` (`1.100.0`) and `hook/build.dart` present while `rust_builder/` was
still wired in (task 1.1, 1.2, 1.4):

- `rustup show active-toolchain` inside `rust/` reports `1.100.0-x86_64-unknown-linux-gnu (overridden by
  '…/rust/rust-toolchain.toml')`, and `cargo test --workspace` passes on it.
- The hook's cargo target directory is `.dart_tool/hooks_runner/shared/<package>/build/<config-hash>/target`, i.e. it
  carries a content hash segment. A CI cache MUST therefore cache the `.dart_tool/hooks_runner/` tree, not a fixed
  path; the hash directory is not predictable across Flutter or dependency changes.
- Cargo really is invoked with `--target <triple>`: the built code asset resolved to
  `…/target/x86_64-unknown-linux-gnu/release/librust_lib_kafkalyzer.so` and that file, not the Cargokit product in
  `build/linux/x64/debug/plugins/rust_lib_kafkalyzer/`, is what ended up in `build/linux/x64/debug/bundle/lib/`.
- `flutter test` did not trigger a Rust compile (31 s suite, 1377 tests green), and `flutter analyze` reports no issue
  for `hook/build.dart`.

## Open Questions

- The hook target directories for macOS and Windows, to be recorded from the CI spike run and checked against the
  Linux-shaped path above before the cache steps are written (task 1.4, 4.3).
- A `flutter build linux --debug` resolved the code asset from the `release` profile directory, so the Rust side looks
  compiled in release mode even for a debug app. Cargokit used the debug profile there. Decide in task 2.x whether to
  pass `buildMode` explicitly: explicit mapping costs a parameter and gives faster dev iteration, leaving the default
  keeps the hook identical to velopack's at the cost of slower debug builds.
- Whether `kafkalyzer-mcp` should inherit the pinned toolchain file (it is inside the same `rust/` workspace, so the
  pin applies to `cargo build -p kafkalyzer-mcp` automatically — confirm no CI step overrides it with `+toolchain`).
