# Design

## Context

See `proposal.md` — Why. The technical starting point:

- `rust/kafkalyzer-kafka/src/kafka_metadata.rs` performs one metadata read (`consumer.fetch_metadata(None, …)`) plus a batched `describe_configs` per topic, and reduces each topic to `name / partition_count / replication_factor / cleanup_policy / retention_ms`. Partition-level objects from rdkafka (`leader()`, `replicas()`, `isrs()`) are never read.
- The same file already decodes consumer-group member bytes (`parse_member_subscription` at `:117`, `parse_member_assignment` at `:154`) but returns only topic names; `ConsumerGroupLag` carries `members_count` and `topics_count` (`rust/kafkalyzer-core/src/kafka_types.rs:72`).
- `rust/kafkalyzer-kafka/src/kafka_consumer.rs` reads the schema id from the wire prefix at `:1266`/`:1333` and resolves it through a mutex-guarded cache (`get_cached_schema`, `:37`), but `KafkaMessage` (`kafkalyzer-core/src/kafka_types.rs:52`) has no place to carry it.
- `TopicAnalysisReport` holds `min/max/avg_message_size` only; the analyzer accumulator already caps `key_counts` at 10 000 entries with an explicit merge guard (`kafka_analyzer.rs:110/225`).
- Consumer lag is a stateless query: `fetch_consumer_lags` returns a snapshot; the Dart view (`consumer_lag_view.dart`) keeps the previous snapshot only to draw `group_delta_badge`.
- Bridge boundary types live in `rust/src/api/` and are mapped with `From`, and the Dart side of every struct is generated by flutter_rust_bridge; mocks live in `test/src/rust/api/rust_mocks.mocks.dart`.

Constraint that shapes everything below: kafkalyzer is read-only. This change may add metadata and consumer reads, never a write, a commit, or group membership.

## Goals / Non-Goals

**Goals:**
- Every new number in the UI is derived from data the application already receives, or from a bounded in-memory summary — no unbounded per-key or per-message memory growth.
- Health and member data reach the UI without multiplying metadata round-trips: one list-level read stays one read, and partition detail is read only for the topic being inspected.
- New report fields stay readable for report files written before this change.
- Percentile and distinct-key figures are labelled exact or estimated, and the estimate is reproducible for the same input.

**Non-Goals:**
- No Kafka write path of any kind (no produce, offset commit, group join, config or ACL change) — this is a standing project rule, not a deferral.
- No new third-party dependencies in Dart or Rust (no t-digest, no HyperLogLog crate, no chart package).
- No lag history persistence across application restarts; no alerting, notification, or server-side storage.
- No change to how topics are listed or filtered; only extra columns/indicators.

## Decisions

### D1. Health counts at list level, per-partition rows on demand

`fetch_topics` returns the existing per-topic fields plus two derived integers per topic: `under_replicated_partitions` and `leaderless_partitions`, classified in Rust as `isr.len() < replicas.len()` and `leader.is_none()`. The topic list and topic sidebar consume only those two integers.

Topic detail calls a new `fetch_topic_partitions(profile, topic)` that issues `fetch_metadata(Some(topic))` and returns one row per partition with `partition`, `leader`, `replicas`, `isr`, `leader_epoch` where available.

Alternative considered: return every partition of every topic in `fetch_topics`. Rejected — a 500-topic cluster with 12 partitions produces ~6 000 rows with three id lists each crossing the FFI on every list refresh, for a view that shows two counts.

### D2. Member identity and assignment come from the bytes we already parse

`parse_member_subscription` / `parse_member_assignment` are extended to return, per member: `member_id`, `client_id`, `client_host`, subscribed topics, and assigned `(topic, partition)` pairs. rdkafka's `MemberMetadata` already exposes client id and host, so no new protocol decoding is needed for identity.

New bridge types `ConsumerGroupMember { member_id, client_id, client_host, assignments: Vec<TopicPartition> }` hang off `ConsumerGroupLag` in `rust/src/api/kafka_types.rs` (bridge-local, mapped `From` the domain type), so the existing lag flow carries members without a second query.

`unassigned_partitions` is derived in the bridge layer by subtracting the union of member assignments from the topic partition counts already known from D1 — no extra cluster call.

Alternative considered: an admin describe-groups request. Rejected: rdkafka 0.36 exposes no convenient typed group description, the bytes are already available, and an admin request would add a round-trip per group.

### D3. Schema provenance is attached in the decode path and cached per schema id

`KafkaMessage` gains `key_schema: Option<SchemaOrigin>` and `value_schema: Option<SchemaOrigin>` with `SchemaOrigin { subject, version, schema_id }`. The values come from the schema id already read from the wire prefix and the entry already cached by `get_cached_schema`; the registry is consulted at most once per schema id per scan session, and a cache miss caused by an unreachable registry leaves the field `None` rather than delaying the message.

Dart reads the fields from the message row it already has; provenance is never fetched per selected message. Alternative considered: resolve provenance lazily from Dart when the inspector opens. Rejected — an FFI call plus registry latency in a selection path, and it would make "does this message use an old schema" unanswerable in the table.

### D4. Percentiles from a bounded deterministic sample; distinct keys from the existing capped map

Percentiles: the analyzer keeps a bounded sample of payload sizes (limit 10 000, matching the existing `key_counts` cap). Sample membership is decided by a deterministic hash of `(partition, offset)` using reservoir/A-Res style priorities, so no RNG dependency exists and the same scan reproduces the same numbers. Worker accumulators merge by unioning samples and re-trimming to the limit. Percentiles are read from the sorted sample; the report records `message_size_percentiles` plus a `size_percentiles_estimated` flag that is false when scanned messages ≤ sample size (exact) and true otherwise.

Distinct keys: report `estimated_distinct_keys = key_counts.len()` plus `key_cardinality_capped` set when the 10 000-entry guard trips. The exact value is already what the existing top-key analysis can support; introducing HyperLogLog would add an estimate where a bounded exact count already exists.

Alternative considered: t-digest / HDR histogram (rejected: new dependency and still approximate), sorting all sizes (rejected: 8 bytes per message, hundreds of MB on a large topic), HyperLogLog for keys (rejected: the map is already bounded at 10 000 and gives exact counts below the cap).

### D5. Report file stays version-compatible

The new report fields are `Option`/`#[serde(default)]` in `TopicAnalysisReport` and the file `format_version` is not raised, so files written by earlier builds import unchanged and older builds ignore the added keys. A report side that lacks a field renders as "not available", never as zero (required by `topic-report-comparison`).

Comparison itself is pure computation over two decoded reports and lives in `kafkalyzer-core` (a `compare_reports(a, b) -> Vec<ReportMetricDelta>` helper) so it is unit-testable without rdkafka and reusable by a later headless surface.

### D6. Lag history lives in the Dart view state; the threshold is a setting

The lag view keeps the last 20 readings per group in a `ValueNotifier<List<int>>` keyed by group id, appended on each successful refresh and cleared when the cluster connection closes. The trend is drawn with a `CustomPainter` in a compact widget next to the existing `group_lag_badge`, and per-partition trends reuse the same widget with the partition series.

The warning threshold is a new integer setting in `SettingsService` (`shared_preferences`, read at view build), defaulting to "disabled" (0). Nothing is stored per group, and nothing is persisted across restarts.

Alternative considered: keep the history in Rust alongside the lag query. Rejected — Rust stays a stateless query layer, the history is view-scoped by design, and a Rust-side cache would survive a reconnect where the spec forbids it.

### D7. UI integration follows the existing surfaces

Partition health: new columns in `topic_partition_table.dart` plus a warning chip on `topic_list_item.dart` when either count is non-zero. Member insights: a member tab inside `group_details_view.dart`. Provenance: two rows in `message_metadata_card.dart` opening the inspector through the existing integrated-inspector entry points. Percentiles and distinct keys: existing summary cards in `widgets/analysis/`. Comparison: a second report picker in the analysis toolbar. All widgets come from `package:material_ui/material_ui.dart`, all strings come from `AppLocalizations` (`app_en.arb` and `app_de.arb` extended with identical key sets).

## Risks / Trade-offs

- Cooperative-assignor groups put partitions in the assignment user data instead of the standard field, so assignment parsing can come out empty for `cooperative` groups → parse both layouts and, when the standard list is empty but user data parses, use user data; when neither yields partitions, show "assignment not decodable" instead of zero.
- New required fields on generated Dart structs break existing call sites and test fixtures → every `KafkaMessage`/`ConsumerGroupLag` construction site and the generated mocks are updated in the same commit; fields are `Option` so no protocol change is implied.
- Percentile figures could be mistaken for exact values on large topics → the label states "estimated over a 10 000-message sample" whenever the estimate flag is set, and the report file keeps the flag.
- Per-topic partition metadata fetch on the detail view adds one round-trip per topic opened → the call is issued once per topic open with the existing metadata timeout, and the list view never triggers it.
- Percentile sample changes the merge path in the analyzer, which partition workers feed concurrently → merge is union-then-trim with a unit test that a two-worker merge equals the single-worker result on the same input set.
- Member lists can be large (hundreds of members on a big connect cluster) → the member tab uses the existing virtualized table pattern rather than a plain column.

## Migration Plan

No data migration. Deployment is a normal build; report files and `shared_preferences` profiles remain readable. Rollback is a plain revert: the report gains only optional fields, the settings gain one unused key, and no Kafka-side state is created by any of these features.

## Open Questions

- Whether `leader_epoch` is exposed by the pinned rdkafka 0.36 metadata API; if not, the partition row omits that column and the remaining fields stand.
- Whether the lag history limit of 20 readings and the 10 000-message percentile sample are the right defaults; both are constants that can be tuned after first field use without changing any spec.
