## Context

Detailed findings and benchmarks are documented in `design/rust-performance-improvements.md`. See `proposal.md` for motivation.

The bottlenecks span the Rust transport/decoding layer (`kafkalyzer-kafka`, `kafkalyzer-core`) and the Flutter FFI consumption layer (`MessageStreamController`, `MessagesTableView`, `MultiSearchController`). This design addresses these bottlenecks systematically across both layers without changing public FFI data models.

## Goals / Non-Goals

**Goals:**

- Eliminate regex recompilation and blocking runtime context-switching inside hot polling loops.
- Cache resolved Schema Registry schemas and reuse Tokio runtimes.
- Decouple Flutter stream consumption from per-message widget tree notifications via 60ms batching/throttling.
- Eliminate $O(N)$ list prepending and blocking synchronous disk I/O on the Flutter UI thread.
- Retain identical UI functionality, filtering semantics, and message ordering across views.

**Non-Goals:**

- Rewriting the Flutter UI with a new component library or changing table appearance.
- Modifying Schema Registry API wire protocol or Kafka broker protocol version.
- Changing FFI struct shapes generated by `flutter_rust_bridge`.

## Decisions

### 1. Pre-compiled Regex Filters & LazyLock Duration Regex

- **Decision:** Pre-compile filter terms into `Vec<Regex>` once before `run_poll_loop` starts in `kafka_consumer.rs`. In `avro_utils.rs`, store the Duration extraction regex in `std::sync::LazyLock<Regex>`.
- **Rationale:** Regex compilation requires significant CPU cycles. Doing it per message drops throughput by >95%. Pre-compiling makes matching $O(M)$ against message content without memory allocation.
- **Alternatives Considered:**
  - Dynamic LRU cache: Adds lock contention in hot loops; unnecessary since filter terms are invariant for a given search session.

### 2. In-Memory Schema Registry Cache & Shared Tokio Runtime

- **Decision:** Maintain a thread-safe, lock-free or read-heavy map (`std::sync::Arc<dashmap::DashMap<u32, Arc<RegisteredSchema>>>` or `parking_lot::RwLock<HashMap<...>>`) in `kafkalyzer-kafka`. Use a shared static Tokio runtime handle (`tokio::runtime::Handle::current()` or `LazyLock<Runtime>`) rather than `Runtime::new()?` per function.
- **Rationale:** Re-creating multi-threaded runtimes creates ephemeral worker threads and epoll/kqueue descriptors. Calling `block_on` inside the message loop for every message halts polling. With caching, known schema IDs decode purely in-memory without async executor yields.
- **Alternatives Considered:**
  - Asynchronous pipeline: `rdkafka::consumer::StreamConsumer` across async streams. Deferred due to extensive architectural refactoring of the sync base consumer.

### 3. Stream Throttling and Circular/Append Buffer in Flutter

- **Decision:** In `MessageStreamController`, buffer incoming messages in a list or ring buffer using `add()` (append) and trim with `removeAt(0)` or reversed display indexing. Throttle `notifyListeners()` with a periodic timer / frame-aligned scheduler firing at most once every ~60ms.
- **Rationale:** Flutter's UI isolate renders at 60Hz or 120Hz. Triggering `notifyListeners()` thousands of times per second wastes CPU on redundant intermediate layouts.
- **Alternatives Considered:**
  - Microtask queuing: Still runs once per message before the next frame, leading to CPU starvation.

### 4. Asynchronous File Logging in MultiSearchController

- **Decision:** Replace `writeAsStringSync` with `IOSink.writeln(...)` or asynchronous streaming sink in `MultiSearchController`.
- **Rationale:** Synchronous disk writes on the UI isolate cause frame drops and noticeable desktop freezes whenever debug logging or message export is enabled.
- **Alternatives Considered:**
  - Separate logging isolate: Overkill for low-to-medium volume text logging; `IOSink` already manages background buffer flushes.

### 5. Viewport-Lazy Formatting in MessagesTableView

- **Decision:** Defer timestamp formatting (`DateFormatUtils.formatDateTime`) and payload preview slicing (`TextPreviewUtils.getPayloadPreview`) until a row's cell is actually requested by `TableView.builder`'s `cellBuilder`.
- **Rationale:** Pre-mapping 1,000 to 2,000 items on every frame update triggers thousands of date and string allocations, even though only ~20 rows are visible on screen.
- **Alternatives Considered:**
  - Virtualized list caching: Kept simple by attaching formatting directly to row accessors.

## Risks / Trade-offs

- **[Memory footprint of schema cache]** → Schemas are small (a few KB each). Even thousands of schemas consume only tens of MBs. Mitigation: bounded cache or session-scoped cleanup.
- **[60ms UI stream latency]** → Messages appear buffered by at most 60ms. Human perception cannot distinguish <60ms delays; 60fps responsiveness remains silky smooth.
- **[Display order with append buffer]** → When appending instead of prepending, UI views that expect newest-first must index from end or flip list view direction. Mitigation: ensure sorting in `MessagesView` correctly preserves view configuration.

## Migration Plan

- Internal performance and architectural improvements only; zero user configuration or schema migration required.
- Full regression testing with `cargo test --workspace` and `flutter test`.
