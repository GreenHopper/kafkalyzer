# Design

## Context

See proposal.md (Why) for the motivation and the spike result. Current state:

- `flutter_rust_bridge.yaml`: `rust_input: crate::api`, `rust_root: rust/`,
  `dart_output: lib/src/rust`. The bridge version is pinned to `=2.11.1` in
  `rust/Cargo.toml` and to `2.11.1` in `pubspec.yaml`. The generator writes a
  version stamp (`@generated by flutter_rust_bridge@ 2.11.1`) into its output.
- Tracked generated files: 20 under `lib/src/rust/`, `rust/src/frb_generated.rs`,
  and 10 `*.mocks.dart` files in `test/`.
- CI job `quality-gates` (`.github/workflows/build.yml`) sets up Rust
  (stable) and Flutter (stable, unpinned), runs `flutter pub get`, then
  `bash scripts/quality_gates.sh`. The generator is not installed there today.
- `scripts/quality_gates.sh` already has guard entry points
  (`cycle-guard`, `locator-guard`, `shared-guard`) and an `is_generated`
  helper. `scripts/test_quality_gates.sh` runs them against fixture repos
  through `KAFKALYZER_REPO_DIR`.

## Goals / Non-Goals

**Goals:**
- A gate run fails when the bridge or mock output does not match its
  generator, both locally and in CI, with the same verdict in both places.
- The guard never destroys uncommitted work.

**Non-Goals:**
- No base-relative comparison: drift is absolute, because a clean tree has
  nothing to tolerate (spike).
- No new Dart or Rust code, and no change to the bridge API.

## Decisions

### D1 — Regenerate in place, diff with git, refuse a dirty start

`check_generated_bindings`:

1. **Version check.** Read the pinned version from `pubspec.yaml`
   (`flutter_rust_bridge: <v>`) and `rust/Cargo.toml` (`=<v>`). If the two
   differ, that is a tooling error. Compare against
   `flutter_rust_bridge_codegen --version`. If the generator is missing or at
   another version, it is a tooling error that names
   `cargo install flutter_rust_bridge_codegen --version <v> --locked`.
2. **Dirty check.** If `git status --porcelain` lists any path under
   `lib/src/rust/`, `rust/src/frb_generated.rs` or `*.mocks.dart`, fail and
   name the paths. Nothing is regenerated.
3. **Regenerate.** Run `flutter_rust_bridge_codegen generate`, then
   `dart run build_runner build`. A non-zero exit is a tooling error that
   prints the generator output.
4. **Compare.** Run `git status --porcelain` on the same paths. Every listed
   path is reported as `bindings guard: <path> differs from generator output`
   (modified) or `... is generated but not checked in` (untracked).

On drift the regenerated files stay in the worktree, so the developer sees
the fix immediately. CI discards its worktree anyway.

Alternative: generate into a temporary `git worktree` and diff there. Rejected:
it doubles the Rust build and the `pub get`, and the dirty check already
protects local work.

Alternative: compare only the version stamp. Rejected: the stamp stays the
same when the API changes, which is exactly the drift we want to catch.

### D2 — Path scope is explicit, not "everything generated"

The guard checks the bridge outputs plus `*.mocks.dart`. It does not use
`is_generated`, because that also matches `lib/l10n/*` and the theme bridge,
which are non-goals (proposal). `build_runner` also rewrites `*.g.dart` and
`*.freezed.dart`. Those are not tracked today (`git ls-files` shows only
mocks), so a newly appearing tracked or untracked one in the listed scope
would be flagged. Outside the scope, untracked build outputs are ignored.

### D3 — Entry point and position in the full gate

Entry point: `bash scripts/quality_gates.sh bindings-guard`. In the full gate
it runs **first**, before `dart format` and `flutter analyze`, because
`flutter analyze` on stale bindings reports confusing errors where the real
fix is to regenerate.

### D4 — CI installs the pinned generator

**Choice: (a)** `taiki-e/install-action` with
`flutter_rust_bridge_codegen@<v>` (reads `<v>` from `pubspec.yaml`).

Spike 1.1 (2026-11-23, local proxy — no remote workflow push yet):

| Method | Cold | Warm | `--version` |
|--------|------|------|-------------|
| (a) `cargo binstall --version 2.11.1` (what install-action uses) | ~33 s (GitHub API 504 retries); download itself is seconds | n/a (binary) | `flutter_rust_bridge_codegen 2.11.1` |
| (b) `cargo install --version 2.11.1 --locked` | ~22 s | ~20 s (still recompiles) | `flutter_rust_bridge_codegen 2.11.1` |

Prebuilt assets exist on the `v2.11.1` release (incl.
`x86_64-unknown-linux-gnu` / musl), and binstall prints the exact pinned
version, so (a) wins: CI gets a binary, not a compile, when GitHub is healthy.
(b) stays the documented local fallback in the tooling-error message.

### D5 — Fixture tests stub the generators

The fixture repo puts fake `flutter_rust_bridge_codegen` and `dart` scripts
first on `PATH`. Each fake prints a version and writes or leaves files
depending on an env var. This keeps the fixtures fast and offline. The real
generators run in the real-repo gate (task 4.x) and in CI.

Fixture cases: clean regeneration passes; modified bridge file fails and names
it; stale mock fails; new untracked generated file fails; generator missing
gives a tooling error; wrong version gives a tooling error; dirty generated
file fails without running the fake generator (the fake records whether it was
called); generator exit 1 gives a tooling error.

## Risks / Trade-offs

- [The generator formats Dart output with the local SDK. CI uses unpinned
  Flutter stable, so a formatter change could create diffs that are not drift]
  → spike 1.2 (2026-11-23): local Flutter stable `3.50.1` (5 days old) +
  generator `2.11.1` left `git status --porcelain` empty for bridge and mocks
  (same as the proposal spike). True remote CI agreement is confirmed when
  the branch is pushed (task 4.2); if CI then diffs, pin Flutter rather than
  narrow the guard.
- [Generator install adds CI minutes] → measured in 1.1. Use the prebuilt
  binary when one is available.
- [`build_runner` resolves the whole package (about 10 s) on every gate run]
  → acceptable. The gate already runs `flutter analyze`.
- [Developers without the generator cannot run the full gate locally] → the
  tooling error names the exact install command. It is the same tool that
  verification step 2 already needs.

## Migration Plan

None: the spike showed zero drift. Roll back by reverting the commit.

## Open Questions

None. The CI install method and CI/local agreement are spike tasks, not
assumptions.
