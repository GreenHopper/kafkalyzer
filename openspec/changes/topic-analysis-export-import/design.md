## Context

See proposal.md for motivation. The relevant current state:

- A finished analysis is a `TopicAnalysisReport` value held only in memory by `TopicAnalysisController` (`lib/src/features/topic/presentation/controllers/topic_analysis_controller.dart`). It is not persisted anywhere; closing the view or restarting the app discards it.
- The dashboard is already rendered by **presentational** widgets that take the report (or its sub-lists) as plain parameters: `TopicAnalysisSummaryCards`, `HourlyProductionChart`, `PartitionBalanceView`, `KeyAndFieldDistributionView`. They have no knowledge of where the data came from — an imported report can be fed to them unchanged.
- The report type is generated by flutter_rust_bridge v2 as a **plain Dart data class** (`lib/src/rust/api/kafka_types.dart`) with `==`/`hashCode` but **no `toJson`/`fromJson`**. It wraps `PlatformInt64` for 64-bit ints.
- The app already has established file (de)serialization patterns to reuse: `file_picker` (`FilePicker.saveFile`, `FilePicker.platform.pickFiles`) for dialogs, `archive` for zip, `path_provider` for directories, and JSON via `dart:convert`. `MessageExportService` (`.json`/`.zip`) and `SettingsService` (profile backup) are the reference implementations.
- Global state (active cluster) is accessed via `getIt` / `ActiveConnectionController`, not prop-drilling.
- The Rust report structs already derive serde `Serialize`/`Deserialize`, but no Rust API exposes (de)serialization today.

## Goals / Non-Goals

**Goals:**

- A single, stable, versioned, self-describing file format for a topic analysis report that carries provenance (source cluster name, export time).
- Export the current report (complete or partial) to a file; import a file and render the full dashboard with no cluster connection and no re-scan.
- Reuse the existing dashboard widgets unchanged and the existing file-dialog/IO patterns.
- Clear, localized success/error UX; reject malformed/unknown/incompatible files safely.

**Non-Goals:**

- In-app persistent "saved reports" history/library or multiple concurrent reports.
- Multi-report bundles or zipping (one file = one report).
- Server/remote sharing or any network transfer (the file is the sharing unit).
- Changing how the analysis scan itself runs (the `topic-content-analysis` capability is untouched).

## Decisions

### D1 — Author JSON (de)serialization in Dart, do not add a Rust bridge function

The report types are simple (strings, 64-bit ints, doubles, bools, nested lists) and are already plain Dart data classes without JSON methods. I will add **hand-written `toMap()`/`fromMap()`** on a small dedicated Dart model and use `dart:convert` to encode/decode.

- **Why**: Keeps the change purely Dart-side — no Rust code, no `flutter_rust_bridge` codegen churn, no new bridge surface. The provenance envelope (cluster name, export time, version) does not exist on the Rust side at all, so we must build the envelope in Dart regardless; building the payload map in the same place keeps the whole file schema in one, testable Dart file.
- **Alternative considered — Rust serde**: Add `serialize_report`/`deserialize_report` to the bridge crate using the existing `Serialize`/`Deserialize` derives. Rejected: it would require a new bridge function plus a full codegen + regeneration step for a trivially serializable value type, and still not provide the provenance envelope. More moving parts for no benefit.
- **Canonical file shape** (snake_case keys, mirroring the Rust serde field names for familiarity):

  ```jsonc
  {
    "kafkalyzer": "topic-analysis-report",   // stable format identifier
    "version": 1,                            // integer format version
    "exportedAt": "2026-08-19T12:34:56.789Z", // ISO-8601 UTC
    "clusterName": "prod-eu-1",              // optional provenance; may be absent/null
    "report": {
      "topic": "orders",
      "total_messages": 1000, "total_bytes": 20480,
      "min_message_size": 1, "max_message_size": 50, "avg_message_size": 20.48,
      "tombstones_count": 0, "is_compacted": false, "null_keys_count": 12,
      "partition_stats": [ { "partition": 0, "message_count": 500, "byte_size": 10240,
                             "percentage": 50.0, "earliest_offset": 0, "latest_offset": 499 } ],
      "hourly_distribution": [ { "hour": 9, "count": 100, "percentage": 10.0 } ],
      "top_keys": [ { "key": "k1", "count": 50, "percentage": 5.0 } ],
      "content_type_distribution": [ { "type_name": "json", "count": 900, "percentage": 90.0 } ],
      "field_frequencies": [ { "field_name": "id", "count": 900, "percentage": 90.0,
                             "top_values": [ { "value": "1", "count": 10, "percentage": 1.11 } ] } ],
      "scan_duration_ms": 12345
    }
  }
  ```

- **`PlatformInt64` handling**: `toMap()` converts 64-bit ints to plain Dart `int` (so the map is `json.encode`-safe); `fromMap()` wraps ints back into `PlatformInt64` when constructing the generated types.

### D2 — A small, dedicated Dart model owns the file format

Introduce one Dart type (e.g. `TopicAnalysisReportFile`) in `lib/src/features/topic/` (or `lib/src/services/`) that:

- Holds the envelope fields (identifier, version, `exportedAt`, `clusterName`) + the `TopicAnalysisReport` payload.
- Implements `toMap()` / `toJson()` and `fromMap()` / `fromJson()`, plus a typed `validate()` that throws a specific, localized-able error (see D5) when the identifier is wrong, the version is unsupported, or required fields are missing/malformed.
- Knows the set of supported versions (currently `{1}`).

Centralizing the schema here keeps it in one place, unit-testable in isolation (no UI, no IO), and gives a single point to evolve the format.

### D3 — A service owns file IO + validation; the controller owns state

- New `TopicAnalysisExportService` (registered in `get_it`):
  - `Future<String?> export(TopicAnalysisReportFile file)` — builds a default filename (`<topic>_analysis_<yyyyMMdd_HHmmss>.json`), calls `FilePicker.saveFile(allowedExtensions: ['json'])`, writes bytes, returns the written path (or null if the user cancelled).
  - `Future<TopicAnalysisReportFile> importFile()` — calls `FilePicker.platform.pickFiles(allowMultiple: false, type: FilePickerType.custom / allowedExtensions: ['json'])`, reads bytes, decodes, `validate()`, and returns the parsed file (throwing a typed error on failure).
- `TopicAnalysisController` gains a **source + provenance** state so the UI can distinguish a live report from an imported one:
  - `enum TopicAnalysisSource { live, imported }` with `TopicAnalysisSource _reportSource` and a getter `bool isImported`.
  - Provenance: `String? reportClusterName`, `DateTime? reportExportedAt` (populated from the envelope on import; for a live report these reflect the current session).
  - `Future<String?> exportReport({String? clusterName})` and `Future<void> importReport()` — thin orchestrators that call the service, update `_report`/`_reportSource`/provenance, and `notifyListeners()`.
  - `startAnalysis(...)` resets `_reportSource` to `live` and clears imported provenance, so a fresh scan is never mistaken for an import.
- **Why this split**: service = pure IO/serialization (testable without Flutter widgets); controller = single source of truth for what the view shows; view stays presentational. This mirrors the existing controller/service split and the "reuse presentational widgets" rule.

### D4 — UI: Export/Import in the analysis controls bar; reuse the dashboard

In `TopicAnalysisView`'s controls bar (`_buildControlsBar`):

- **Import** button — always enabled; on tap, run the import with a loading state, then render the dashboard (which already shows when `report != null`).
- **Export** button — enabled only when a report is available; on tap, run the export with a loading state.
- **Imported indicator** — when `controller.isImported`, show a Material `Chip`/label reading "Imported from `<clusterName>` · <export time>" using `package:material_ui`. A live report shows no such chip.
- All async actions show visual feedback (spinner/disabled button) and surface errors via a `SnackBar` (per the UI/UX guidelines). Buttons come from `package:material_ui/material_ui.dart`.
- **Localization**: every new label, chip text, success message, and error message is added to `app_en.arb` and `app_de.arb` and consumed via `AppLocalizations`.

### D5 — Explicit import error model

Define a small sealed set of import outcomes so each failure maps to a distinct, localized message rather than a raw exception string:

- `notAnAnalysisFile` (missing/wrong `kafkalyzer` identifier)
- `unsupportedVersion` (identifier ok, version not in the supported set) — include the found version in the message.
- `malformed` (JSON parse failure or required report field missing/typed-wrong)
- `ok` (parsed + validated)
Export failures (write error) map to a generic localized "could not write file" message. The service throws/returns these; the view/controller maps them to SnackBar text via `AppLocalizations`.

### D6 — Cluster name is best-effort provenance

At export, capture the active cluster name via `getIt`/`ActiveConnectionController` when available; if none is active, omit it (`null`). It is metadata for humans and the imported indicator — import/viewing never depends on it.

## Risks / Trade-offs

- [Generated types lack JSON methods; hand-written maps could drift from the Rust schema] → Keep the map in ONE model (D2) with a unit test that round-trips a representative report through `toJson` → `fromJson` and asserts field equality; treat the canonical shape (D1) as the contract.
- [`PlatformInt64` is not `json.encode`-safe] → Convert to plain `int`/`double` in `toMap()`, wrap back in `fromMap()` (D1); covered by the round-trip test.
- [A future version change could break old files] → Version-gated validation (D2/D5) rejects unsupported versions with a clear message; additive fields should be optional with defaults on `fromMap()` so older files still import into newer apps.
- [A stale imported report could be mistaken for a fresh scan] → The mandatory "Imported" indicator + provenance chip (spec: *Distinguish imported reports*; D4).
- [Large reports (many partitions/fields/top values) produce large files] → Acceptable; reports are bounded by Top-10 values and per-partition/field aggregates, not raw messages. No compression needed.
- [Sensitive data in shared files] → Reports contain only aggregate statistics (topic name, key/field names and top *values*) and no cluster credentials or secrets; still, treat sharing like any data export. No credentials are stored in the file.
- [`file_picker` API drift across platforms] → Reuse the exact `FilePicker.saveFile` / `pickFiles` calls already proven in `MessageExportService`/`SettingsService`.

## Migration Plan

- Purely additive; no data migration, no changes to existing Rust↔Dart API signatures, no new packages.
- Rollout: add model + service + controller state + view wiring + l10n, ship. Existing live-analysis flow is unchanged (a live scan sets `source = live`).
- Rollback: removing the feature reverts the new files/wiring; the report format is forward-compatible (v1) and no persisted state is introduced.

## Resolved (confirmed by user)

- **Entry point**: Keep it in the topic analysis view (per-topic). No global "Import an analysis report" entry point for now; it remains a possible follow-up that would not change the file format or the spec.
- **Filename default**: Keep the suggested default `<topic>_analysis_<yyyyMMdd_HHmmss>.json`; the user may still override the name in the save dialog.
